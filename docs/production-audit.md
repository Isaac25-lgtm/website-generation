# ImprintSites production audit

20 November 2026 · Source reviewed against `80b951b` · Release decision: **hold paid launch**.

The builder, editor and hosted storefront are implemented. A customer can already lose inventory variants or publish inconsistent prices during ordinary merchant workflows. Several failures also sit behind features awaiting credentials. Resolving the currency, inventory, draft-saving and payment defects will do more for launch readiness than changing programming languages alone.

## What runs today

The React app in `src/client` talks to a Hono API in `src/worker`. One Cloudflare deployment serves both the SPA and the API. D1 holds users, hashed sessions, intake, drafts, versions, products, inventory, orders, leads and billing records. Media uses D1 with an optional R2 adapter. Hosted customer sites are rendered on the server from a versioned JSON document called SiteDoc. The store catalog and inventory are read separately from current database rows.

The homepage description fills in a bio or description field. The wizard, selected template and deterministic generator produce the initial pages. Opt-in Workers AI copy polishing rewrites selected fields. The editor can ask the model for a constrained theme or hero-layout patch and falls back to rules. Inspiration analysis reads browser or HTML/CSS signals, with local colour sampling for screenshot uploads. The deployed model binding is configured for Meta Llama 3.3 70B Instruct. The model runs at the provider. The codebase contains no tracked Python application. ## High priority

| Finding and consequence | Repair and acceptance criterion |
|---|---|
| **1. Store currency diverges during onboarding. Reproduced.** The wizard prices items using the selected currency. Product creation looks for an already-generated draft and defaults to USD. The product page uses the product currency, while checkout uses the published store currency. For a manual price of 10,000 UGX, the persisted 10,000 minor units can display as USD 100 on the product page. CSV import also converts amounts using the backend default, which can inflate the checkout amount in a zero-decimal currency. [Wizard](../src/client/app/Wizard.tsx#L73) · [Currency lookup](../src/worker/routes/commerce.ts#L19) · [Checkout](../src/worker/routes/public.ts#L173) | Persist the store currency before the first product. Use it in the UI, import, product records and orders. Define how currency changes affect existing prices. Review affected records before changing amounts. Test manual and CSV prices in UGX and USD from setup through an actual order. |
| **2. CSV updates delete variants. Reproduced.** A product-level SKU match supplies one variant to a full replacement writer. The writer deletes omitted variants. A two-variant notebook became a one-variant product after a title and price update. [Import](../src/worker/routes/commerce.ts#L234) · [Variant removal](../src/worker/routes/commerce.ts#L138) | Distinguish product updates from variant replacement. Match explicit variant identifiers, preserve omitted variants and return per-row validation errors. Re-import the same file twice and verify IDs, options, inventory and outstanding orders. |
| **3. Saving product details can reverse sales.** The merchant form sends the absolute stock from when it opened. The API assigns it on every edit. A title change after a sale can restore the sold quantity and record it as a manual adjustment. The checkout trigger guards only the decrement. [Merchant form](../src/client/app/Store.tsx#L82) · [Variant update](../src/worker/routes/commerce.ts#L126) | Separate stock adjustments from catalog edits. Apply quantity deltas or conditional updates against a known inventory revision. A title-only edit after a sale must preserve the post-sale count. |
| **4. Draft conflict checks can admit two writers.** A request compares the revision in memory, then saves by project ID alone. Two simultaneous saves of the same revision can both return success. The editor also catches save failures internally, allowing a subsequent template or AI action to proceed from older server data. [Revision check](../src/worker/routes/projects.ts#L310) · [Write](../src/worker/lib/site.ts#L138) · [Editor](../src/client/app/Editor.tsx#L58) | Make the revision a database write condition. Tie the history and index updates to the winning write. Serialize browser saves and stop dependent actions on failure. Test two active editors and a failed save immediately before switching templates. |
| **5. Billing events can be lost or applied out of order.** A delivery left in `received` after a Worker interruption is acknowledged as a duplicate on retry. A refund arriving before its local payment is marked ignored. Concurrent success deliveries can both pass the entitlement existence check because there is no unique payment-to-entitlement constraint. Every successful refund also maps to a full revocation. [Delivery lifecycle](../src/worker/routes/billing.ts#L73) · [Grant and refund](../src/worker/routes/billing.ts#L115) · [Schema](../migrations/0001_initial.sql#L468) | Use a recoverable webhook inbox, uniqueness per payment, and reconciliation against the provider’s payment and refund state. In staging, verify success, duplicate, interrupted processing, full and partial refund, and refund-before-success. Confirm the grant and publication state after every case. |
| **6. Publication can outlive its grant.** Revoking a demo grant updates the entitlement alone. The published route serves a live row without consulting the applicable entitlement. A switch from test to live also leaves already-published test sites reachable. Refund logic counts any active source, including sources invalid in live mode. [Admin revoke](../src/worker/routes/admin.ts#L88) · [Public serving](../src/worker/routes/sites.ts#L41) · [Mode-specific grants](../src/worker/lib/site.ts#L94) | Use one entitlement policy during grant changes, mode transitions, public serving and storefront writes. Reconcile existing sites at cutover. Verify that revoking the last eligible grant takes both pages and order intake offline, while another eligible grant keeps them live. |
| **7. Google account linking can select the wrong identity.** The callback accepts a match by email even if the local account already has a different Google subject. It then issues a session. This matters before enabling Google, particularly for reassigned organization addresses. [Callback](../src/worker/routes/auth.ts#L99) · [Google identity guidance](https://developers.google.com/identity/openid-connect/openid-connect) | Require the stored provider subject to match for previously linked accounts. Handle linking and account recovery as explicit flows. Verify that an email collision between distinct subjects cannot create a session. |
| **8. Private inspiration media can become public.** The screenshot uploader uses the normal public upload path. Browser-captured references are stored privately, but the export selects all project assets, so uploading the ZIP to a static host can publish those reference files too. [Upload flow](../src/client/app/Wizard.tsx#L123) · [Visibility default](../src/worker/routes/assets.ts#L41) · [Export](../src/worker/routes/projects.ts#L506) | Classify reference uploads as private at creation, verify their project ownership and export only publishable assets actually referenced. Check direct access and ZIP contents for both kinds of reference. |
| **9. Browser inspiration validates navigation too late.** Browser Run visits the URL before checking its final destination. The app does not apply the HTML fallback’s outbound policy to every redirect and subresource before the browser requests it. Runtime network isolation was not independently verified. [Browser navigation](../src/worker/lib/inspiration.ts#L212) · [Fallback fetch](../src/worker/lib/ssrf.ts#L77) | Enforce the outbound policy before browser requests, including redirects and subresources, or restrict the feature to the bounded HTML path until equivalent controls are verified. |
| **10. Missing signing configuration silently uses a built-in key.** Preview and order token functions use a shared fallback whenever the secret is absent. A misconfigured environment can issue and accept predictable signatures. The health endpoint only checks D1. [Signing](../src/worker/lib/site.ts#L102) · [Health check](../src/worker/index.ts#L36) | Require a configured signing key, fail closed on private links, and validate required secrets before traffic is enabled. Exercise the missing-secret case and document rotation effects. |

| **AI accounting and smoke checks overstate reliability.** Enforcement counts failed and successful AI jobs, while the dashboard reports successes alone. ## Recommended separation

Keep one repository with separate build, test and deploy entry points for the React frontend and the Python API. Django with PostgreSQL is a good fit for the requested target because orders, refunds, stock and publishing need conditional writes, transactions and database constraints. The existing React admin can remain a client of that API. A temporary TypeScript rendering service can continue to turn SiteDoc into public HTML while the API moves. Give the Python service sole ownership of customer and business data as each feature moves.

| Boundary | Responsibility |
|---|---|
| React frontend | Marketing, wizard, editor and merchant dashboard. Call a versioned HTTP API. Keep provider credentials and authoritative prices on the server. |
| Python API | Identity, project access, draft revisions, billing, product currency, inventory, order transitions, signed links and media permissions. Own the schema, migrations, OpenAPI contract and provider adapters. |
| AI jobs | Accept a customer brief, run the configured provider, validate structured output, persist the resulting draft, and record attempt, latency, usage and outcome. Python can call Workers AI over its authenticated REST API. [Workers AI REST API](https://developers.cloudflare.com/workers-ai/get-started/rest-api/) |
| Site renderer | Consume the versioned SiteDoc and scoped catalog data. Preserve published URLs, preview links, media links, and existing customer templates. Route storefront writes to the API. |

**Migration order.** First put tests around the reproduced currency and variant bugs, stale inventory writes, draft conflicts and payment event recovery. Fix defects that affect the running service while migrating. Next establish the Python API contract and migrate a read-only project/preview workflow against staging fixtures. If a single prompt should design a site, add a planning call that proposes pages, sections and follow-up questions and validates the result against SiteDoc. Test this separately from copy polishing. Move mutations one domain at a time with a single active writer, preserve identifiers and session compatibility, rehearse data migration and rollback, then compare public renders and order totals before routing production traffic. Preserve the existing one-time USD 20/30/100 build fees and the announced USD 4/month fee throughout.

**Paid launch gate.** Prove a clean build and restore, a UGX order, a USD order, a concurrent stock change, a draft conflict, a complete externally hosted export, and the Dodo test-mode purchase → publication → refund → withdrawal lifecycle. Record provider configuration and results separately from fallback behavior. Google, custom domains and seller card acceptance can have independent activation dates.
